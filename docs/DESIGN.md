# Design: data and modules

Design notes for plandoll. This file describes the data and the modules.

## 1. Pipeline

```
plan JSON (format v1, see docs/SPEC.md sections 1 to 4 and docs/PROMPT.md)
  -> analyzePlan / modelOf   (src/core/validate.js)       validated plan, units converted to metres
  -> buildModel              (src/model/geometry.js)      walls with thickness, openings with positions, rooms, colliders
  -> autoFurnish             (src/layout, pure functions) layout = list of pieces with positions
  -> PlanScene, composeLayout (src/render/scene.js, src/render/compose.js, src/furniture)
                                                          THREE objects: shell (walls, floors) + one object per piece
  -> look                    (src/look)                   light, shadows, post-processing, backdrop, quality level
  -> frame
```

The page never sends anything anywhere. No network requests, no localStorage, sessionStorage, cookies or IndexedDB.

## 2. Coordinates and angles

- Plan space: x to the right, y down the page, metres. World (three.js): x = plan x, z = plan y, y up. A level's floor is at `level.elevation`.
- `rot` is degrees clockwise as drawn on the plan (the same as `furniture.rotation` in the plan format). In three.js set `object.rotation.y = -rot * Math.PI / 180`.
- Every piece is built in its local frame: x = width, z = depth, y up, FRONT faces +z, BACK is -z, origin at the centre of the footprint on the floor. With `rot = 0` the front looks down the page (south). `rot = 90` looks west, `180` north, `270` east.
  So a sofa with its back on the north wall (small y) has `rot = 0`; with its back on the east wall `rot = 90`; on the south wall `rot = 180`; on the west wall `rot = 270`.
- Beds follow the same rule: width along x, headboard at -z, foot at +z. (The bed in `src/furniture/legacy.js` has the long side along x: do not mix them. `legacy.js` exists only as a stop-gap until a type has a new builder.)

## 3. The three documents

**Plan** is the v1 JSON described in `docs/SPEC.md` (walls, openings, rooms, optional stairs). Furniture in an input plan is ignored: the layout comes from the engine.

**Layout** is plain data, the thing an editor will change later:

```json
{
  "version": 1,
  "seed": 1,
  "levels": [
    {
      "id": "L0",
      "pieces": [
        { "id": "p1", "type": "sofa3", "room": "main", "x": 3.2, "y": 1.4, "rot": 90,
          "size": [2.1, 0.95, 0.85], "elev": 0, "on": null, "colors": { "upholstery": "#c9b8a6" } }
      ]
    }
  ]
}
```

- `type` is an id from `src/furniture/specs.js`. `x`, `y` are the centre of the footprint in plan metres. `size` is optional (default: the spec) and must stay inside `range`.
- `elev` is the height of the piece's bottom above the level floor (default 0; wall-mounted pieces use `place.elevation`; for a ceiling lamp it is the bottom of the hanging part).
- `on` is the id of the piece this one sits on (props on tables, shelves, nightstands); then `x`, `y`, `elev` are absolute anyway. It lets an editor move the child with its parent.
- `colors` maps a slot name to a colour in one of three forms: `#rrggbb` (stored lower case), `lib:<key>` (a material of the library, `src/render/library.js`) or `f:<key>` (a material of the furniture kit such as `f:wood`; pieces only). A bare library key (`oak`, the spelling of older files) is read as `lib:oak`; whatever is written uses the full form. Missing slots use the piece's default.
- Limits: at most 400 pieces per level and 1500 in total; ids unique; every number finite. `autoFurnish` returns exactly this shape and nothing else.
- `levels[].rooms` is optional and maps a room id of the plan to `{ "wall": colour, "floor": colour }` (each part optional, a colour is `#rrggbb` or `lib:<key>`, never `f:<key>`; at most 200 rooms per level): a file without it is still a valid version 1 layout and `autoFurnish` never returns it.

**Style** is also plain data:

```json
{ "preset": "amber", "t": 0.735, "quality": "auto" }
```

`t` is the time of day from 0 (06:00) to 1 (23:00). `quality` is `auto`, `high`, `medium` or `low`. Per-room floor and wall colours are not part of the style: they live in the layout (`levels[].rooms`).

## 4. Furniture (src/furniture)

- `specs.js` is pure data for every type (size, range, placement rules, rooms, slots, emitters, triangle budget). It is the single source for the layout engine and for the tests of the builders.
- A builder is `buildPiece(type, { size, colors, seed, quality }) -> THREE.Group`. The group carries `userData = { type, size, tris, slots: [...], emitters: [...] }`. Meshes carry `userData.slot`. Static geometry is merged per slot, so a piece costs a handful of draw calls, not dozens.
- `emitters` are `{ pos: [x, y, z] (local), color, power }` for lamps. The look decides how many become real lights (a small fixed number) and how many are only glow.
- Everything is built from code. No model files, no texture files, no fonts, no network. Randomness only through a seeded generator (`mulberry32(seed)`), never `Math.random`.
- Loops use counters with limits. A piece that hits a limit sets `userData.truncated = true` instead of freezing the page.

## Editing pieces (src/furniture)

An editor changes the Layout document (section 3, format unchanged, version 1) and asks the furniture module for the data it needs and for rebuilt pieces. Nothing here touches the plan.

**Fields of a layout piece an editor may change**

| field | what it is | allowed values |
| --- | --- | --- |
| `x`, `y` | centre of the footprint, plan metres | finite numbers; keeping pieces apart and inside the room is the editor's job |
| `rot` | degrees clockwise as drawn on the plan | any finite number (turn in steps of 90 or freely) |
| `size` | `[w, d, h]` in metres | each axis that has a range in `specs.js` (`range.w`, `range.d`, `range.h`) inside it, every other axis the default; `clampSize` does this |
| `colors` | `{ slot: colour }` | slots from `spec.slots`; a colour is `#rrggbb`, a material of the library as `lib:<key>`, or a kit material `f:<name>`; a slot that is missing (delete the key) keeps the default |
| `elev` | height of the bottom edge above the level floor | edited for `wall-mount` and `ceiling` pieces, default `place.elevation` (`elevation` in the catalogue); for a `surface` piece it is the height of the top of the piece it sits on and follows `on`; every other piece stays at 0 |
| `on` | id of the piece it sits on | only for `surface` pieces, and only a piece whose type is in `place.onTop` (`onTop` in the catalogue); `x`, `y`, `elev` stay absolute |

`type` is not edited in place: a different type is a new piece (remove one, add one), chosen from the catalogue.

**Library keys for `colors`.** `lib:plaster-warm`, `lib:plaster-cool`, `lib:limewash`, `lib:oak`, `lib:oak-smoked`, `lib:walnut`, `lib:tile-grey`, `lib:stone-light`, `lib:boucle`, `lib:linen`, `lib:velvet`, `lib:leather`, `lib:lacquer-white` (`MATERIAL_KEYS` in `src/render/library.js`). A `#rrggbb` colour is the colour the surface should have on the whole: a textured surface keeps its structure and is tinted towards it. A slot with vertex colours (books, leaves, stems) multiplies the tint with them, so books stay varied.

**Data for the interface (pure functions, no three.js in `catalog.js`)**

- `catalog(lang)` (`src/furniture/catalog.js`): the list of pieces to choose from, `{ id, group, groupLabel, tier, label, size, range, slots: [{ name, label }], rooms, mode, elevation, onTop }`, ordered by group (the order of `GROUPS`), tier and id; `lang` is `'en'` or `'pl'`. `catalogGroups(lang)` gives the same as `[{ group, label, items }]`. Tier 3 entries (sideboard, vase, small wardrobe, sofa bed, wall shelf, bathroom cabinet and the other extras) are never placed by `autoFurnish`, which uses tiers 1 and 2; they are there for the person who edits.
- `defaultSizeOf(type)`, `clampSize(type, size)` (millimetres, held inside the range, a value that is not a finite number is replaced by the default of that axis), `isResizable(type)`, `resizableAxes(type)`, `slotLabel(type, slot, lang)`.
- `paletteOf(type, slot)` (`src/furniture/palettes.js`): `{ id, label, colors: [{ hex, name: { en, pl } }] }` with 8 to 12 colours, chosen from the material the builder uses for the slot (wood, fabric, painted, metal, ceramic and gloss, greens, glass and screens, picture tint). `defaultColorOf(type, slot, look = 'textured')`: the `#rrggbb` the slot has in that look. It is read from a piece built by the code (the flat colour of the clay look); for the textured look the colour of the material from `LOOK_COLOR` (`src/render/materials.js`) takes its place where the table has one (taupe sofa, walnut furniture, terracotta pots, green leaves); for a slot with vertex colours the result is the average. Only `'clay'` gives the flat colour.

**Rebuilding.** `rebuildPiece(group, { size, colors, quality, look })` (`src/furniture/index.js`) returns a new group for the same piece with the changes applied:

- `size` entries that are not finite numbers keep the current value; the result is held inside the range. `colors` is merged into the colours the piece already has (`userData.colors`); `null` brings the default back; unknown slots and invalid colours are dropped. `quality` and `look` default to what the piece had (`userData.quality`, `userData.lookName`, the latter set by `applyLook`).
- The new group takes the place of the old one: position, rotation, scale, visibility and name are copied, it sits at the same index among the children of the same parent, and every field of `userData` other than the ones the builder owns (`type`, `size`, `tris`, `slots`, `emitters`, `truncated`, `builder`, `seed`, `quality`, `colors`, `lookName`) is kept, so `pieceId`, `levelId`, `elev` and `pieceType` survive. The seed is kept, so a rebuild without changes gives the same geometry.
- `userData.emitters` come from the new build (local positions). A list of lights in world space made from the old group has to be made again from the new one (`emittersOf` in `src/render/compose.js`).
- The geometries of the old group are disposed; materials are shared and stay. Children that a caller added to the old group are not carried over. Rebuild a piece when its size or colours change, not on every pointer move: a drag of the position only moves the group.
- Tinted materials are cached by colour; the cache is bounded (about 1500 entries, the oldest half is dropped when it overflows), so a free colour picker does not grow memory without limit.

**Rooms.** `ROOM_PALETTES` (`src/furniture/palettes.js`) holds `wall` and `floor` lists of 8 to 16 entries `{ value, swatch, name: { en, pl } }`: `value` is what a layout stores for the room (`#rrggbb`, or `lib:<key>` of the material library) and `swatch` is the colour to draw in a picker (for a library surface its average colour). The flat colours come first, the library surfaces (plasters and limewash for walls, boards, tile and stone for floors) last. `roomPalette(kind, lang)` gives one list with the names in one language, or `null` for an unknown kind. The lists only offer colours; applying a colour to a room is the job of the scene (section "Surfaces"). The palettes of pieces (`PALETTES`) end with a few library surfaces in the same way (`{ hex: 'lib:oak', swatch, name }`); every value passes `isSlotColor`.

### Panel (src/app/panel.js)

`createPanel({ doc, host, lang, session })` returns `{ element, refresh(), setLang(lang), dispose() }`. It adds one element (`#ps-panel`) to `host` (the body when missing) and, once, a `<style id="ps-panel-style">`; all its class names start with `psp-`. It keeps nothing in the browser, makes no requests and does not move, turn or delete a piece (that is the edit bar of the page), nor does it read or write files.

It has two parts. **Add**: a button that opens a list; the groups of `catalogGroups(lang)` are collapsible sections (the first one starts open), every entry is a button at least 44 px high with the name, a tag for the extras (tier 3) and the rooms the piece suits (the first three, then a count). **Selected piece**, shown while `selected()` is not `null`: the name of the type, the problems of the piece as short lines, one number field in centimetres for every axis that has a range (`resizableAxes`, `min` and `max` from the range, step 1), and for every slot a bar of swatches: a "Default" swatch that shows `defaultColorOf(type, slot)` followed by the colours of `paletteOf(type, slot)`. A swatch is a button with `aria-pressed`, its name in `title` and `aria-label`.

**Selected room**, shown while `selectedRoom()` returns a room and no piece is selected (a piece wins if a session reports both): the name of the room and two bars, "Walls" and "Floor", each with a "Default" pill (`recolorRoom(part, null)`) and one swatch per entry of `roomPalette('wall' | 'floor', lang)`; a swatch calls `recolorRoom(part, value)`. The pressed swatch is the one whose value equals the room colour (`#rrggbb` without regard to case, `lib:` keys literally). A switch "Snap to neighbours" (`role="switch"`) is shown whenever the sheet is open and the session has `snapEdges` and `setSnapEdges`; it flips the setting.

On a screen 760 px wide or narrower the sheet floats above the bars of the page: its bottom edge is `--ps-stack-h` (pixels, read from the root element, with or without `px`; 200 px while it is missing) plus 8 px, it is at most 40 percent of the screen high and scrolls; the button stays at the top right. Wider screens get a column at the top right (the list of pieces scrolls inside the column so that the selected piece stays in view below it). Escape closes the list.

What the panel needs from the session (`src/app/edit.js`; the tests use a stand-in with the same methods):

| call | use |
| --- | --- |
| `selected()` | the selected layout piece `{ id, type, size?, colors? }` or `null`; the second part is rebuilt when `id` or `type` changes, otherwise only values are synced |
| `problems()` | a list of `{ kind }`; `overlap`, `outside-room`, `floating-prop` are drawn red, `door-zone`, `stair`, `tall-before-window`, `unknown-type`, `bad-number` yellow, other kinds are not listed |
| `add(type)` | called when an entry is touched; `{ ok: false, reason }` keeps the list open and shows a sentence for `no-room`, `limit-level`, `limit-total` (any other reason gets a general one) |
| `resize({ w, d, h })` | metres, all three axes, held in the range by `clampSize`; called on `change` of a field and only when the value differs from the one in use |
| `recolor(slot, color)` | a `#rrggbb` or `lib:<key>` of the palette, or `null` for the default |
| `selectedRoom()` | `{ level, id, name, colors: { wall?, floor? } }` or `null`; optional |
| `recolorRoom(part, color)` | `part` is `'wall'` or `'floor'`; a `#rrggbb` or `lib:<key>` of the room palette, or `null` for the default; optional |
| `snapEdges()` and `setSnapEdges(bool)` | the snap to the sides of neighbouring pieces; the switch shows only when both exist |
| `subscribe(fn)` | any event refreshes the panel; the function it returns is called by `dispose()` |

`refresh()` rebuilds only what changed. A field that has the focus keeps what is typed, and the number of nodes does not grow with the number of refreshes. `setLang(lang)` switches every text (`'pl'` or `'en'`). `tools/panel-live.mjs` drives the real page with `edit=1` and a real session through `tools/shot.mjs` (open the list, select a piece, change a size and a colour, select a room and change its colours; one screenshot per step and viewport, plus a printed audit of touch targets under 44 px, overlaps with the bars and parts beyond the right edge). `tools/panel-sheet.mjs` builds a review page of the panel with the real catalogue and a stand-in session (see the header of `tools/panel-entry.js` for the hash options, among them `room=1` and `pickroom=wall.2`; the page sets `--ps-stack-h` to 190 px like the page of the product does).

## Surfaces (src/render/scene.js, src/render/materials.js)

`PlanScene.setRoomColors(colors, look)` gives rooms their own wall and floor colours. `colors` is `{ "<level id>": { "<room id>": { wall?, floor? } } }`; a value is `#rrggbb` or `lib:<key>` of the material library, anything else (wrong format, unknown key) counts as no colour; unknown levels and rooms are ignored (own properties only). The call is idempotent: the same colours give the same scene, and with no colours the scene is the one the constructor built (same materials, same geometries, same meshes). A `look` of `'clay'` or `'textured'` that differs from the scene's look is applied to the whole scene first (`setMaterials`).

- **Floors.** The floor mesh of every room (`room:<id>/floor`) takes `paintMat(name, color, look, true)` from `src/render/materials.js`: a copy of the floor material of the room in which the texture keeps its structure and its average becomes the colour (clay look: the flat colour). A `lib:<key>` value uses the surface of the library instead and the uv of the floor are written again for its repeats per metre (the old geometry is disposed). `null` brings back the shared default material and the first uv.
- **Walls.** Only the faces that look into the room are painted, by a skin: a thin quad (a geometry of its own, 4 vertices) 2 mm in front of the wall face, for one wall piece, one side and one stretch of that side along which one room looks at the wall. The stretches come from sampling the room polygons 3 cm beyond the face every 10 cm and refining each end by bisection, so a wall shared by two rooms gets two skins in two colours, and the far side of the wall (another room, or the outside) stays as it is. The pieces around windows and doors are separate wall pieces, so a skin never covers an opening. A skin follows its wall piece: it is cut with `setCut` (never below the floor), hidden when its piece is hidden, and its uv keep the scale of the texture. Skins are created on demand, named `skin:<level>:<wall>/<piece>/<side><n>`, and removed when the colour goes; the number of skins depends only on the colours given.
- **Looks.** Painted surfaces carry `pw.paint`, so `setMaterials(look)` re-applies them for the other look; the mood (amber, clear, lamplit) only changes light and never the colour of a room.
- **Memory.** `paintMat` keeps its copies in a cache of at most 48 entries (oldest dropped and disposed first), so 200 calls with changing colours do not grow materials; `disposeMaterials()` frees it. Tests: `tests/render/room-colors.test.mjs`. Review page: `tools/rooms-entry.js` (build with `tools/build-sheet.mjs`).
- **Hostile plans.** `tests/render/hostile-scene.test.mjs` builds `PlanScene` and `composeLayout` (on an automatic layout) from plans that pass the validator but sit at its edges: 200 rooms on two levels, 150 rooms on one, twelve levels of 40 rooms, rooms of 0.5 m2, a room polygon with 120 points, 600 walls in one room, a 150 m hall with 3 m thick walls next to a 100 m sliver, levels 12 m and 40 m high. Each case must finish in under two seconds in Node, throw nothing, keep every vertex position finite and stay inside limits (scene: 20,000 meshes and 1,000,000 vertices; furnishing: 10,000 meshes and 3,000,000 vertices). The biggest case measured (twelve levels of 40 rooms) has 11,040 scene meshes and 251,520 vertices, 3,964 furnishing meshes and 1,062,491 vertices, and builds in well under a second. Plans the validator rejects (a room under 0.5 m2, a plan wider than about 200 m) never reach the scene builders.
- **Contact shadows.** `src/render/contact.js` gives every piece that stands on the floor (place mode `floor` or `corner`, not lifted) a soft dark footprint: a 3 x 3 patch (a solid middle, a soft rim at most 0.2 m wide) under the part of the piece that touches the floor. `mergeByMaterial` adds all patches as one extra mesh named `contact-shadows` (one more draw call for the whole home); it is never picked, casts and receives no shadow, and its vertices carry upward normals because the occlusion pass reads the normals of every mesh. Pieces left out of the merge (`skip`) and hidden pieces get none. `setContactLook(k)` (called by the stage) takes the colour from the ground light of the hour and the strength from the sun. In edit mode, where meshes are not merged, there are no patches.
- **Window panes.** The glass material shows a small grey sky and skyline texture (`window-view`, 128 x 64, drawn once by the stage) as colour and emission, so the pane takes its tint from the glow colour of the hour: no extra mesh and no extra draw call per window.
- **Door handles.** Every door leaf gets one small steel bar at hand height (`PlanScene._handle`), registered with the cut walls so that it hides and shrinks with them.
- **Window light.** `src/render/sunpatch.js` draws one soft warm patch per window on an outer wall of a room, all in one mesh (one draw call, flat stand-in positions and upward normals for the ambient occlusion pass, never picked). The shape is computed in the vertex shader from the four corners of the opening and one sun direction (`setSunPatchLook(k, dir)`, called by the stage with every hour): where the sun is outside the window the opening is projected along the rays onto the floor (at most 4.2 m long), otherwise a faint pool of sky light lies just inside. The patch is added blended, fades out at night, hides while the levels are exploded, and `applyWallCut` switches the patch of a pane with the pane (`userData.show`).
- **Cut window panes.** A pane that the cutaway leaves as a thin strip is hidden together with the wall above it; left in place it glows like a light bar at night.
- **Wall feet.** Wall materials darken a little (down to 0.8) over the first 0.7 m above every floor, by a small shader hook (`footShade` in `src/render/materials.js`; the floors come from `setWallFloors`, called by the scene), so rooms read as lit from above without extra geometry.
- **Curtains.** `pleated(..., { uneven: true })` gives every fold its own width and depth and a slow drift along the rail, so a wide curtain does not read as regular stripes.

## 5. Layout engine (src/layout)

Pure functions, no three.js, no DOM, runs in Node. Input: the built model (`buildModel` output) plus options `{ seed }`. Output: a layout (section 3).
Room type comes from the room name (Polish and English, case and diacritics insensitive) or `room.use`, else from the geometry (area, doors, windows, neighbours). Placement honours `specs.js` (`place.against`, `clearFront`, `clearSide`, `rooms`), keeps door zones free (0.8 m in front and behind each door, plus the swing), keeps tall pieces away from windows, and is deterministic for the same input and seed. A kitchen of 11 m2 or more gets a table with four chairs only where table and chairs also stay out of the free strips in front of the units, so the automatic layout of the example plans and the generated plans has at most two pieces per plan with a blocked front.

The recipes (`recipes.js`) also use four types of the extended catalogue, only when the caller allows them (`allowedTypes`; the default set of the engine has none of them): `sofa-bed` first in a living room under 16 m2 (an ordinary sofa is the fallback, so every living room keeps its sofa), `wardrobe-small` when a bedroom has no room for a full wardrobe and in halls that are too narrow for one, `shelf-wall` above a chest of drawers, sideboard, desk or shoe cabinet and once on the wall of a hall (wall-mounted at least 1.2 m up, kept clear of windows and doors like every wall-mounted piece), and `bathroom-cabinet` above the washbasin in place of the plain mirror. `checkLayout` counts a `sofa-bed` as the sofa of a living room.

Every living room, dining room, bedroom, children's room and office ends with at least one light: when a recipe has not placed a lamp, a standing lamp goes in the free corner closest to the main piece and, if no corner is free, a pendant hangs over the roomiest floor.

Three rules refine the recipes. A living room first looks for a sofa that faces the television within 24 degrees (against a wall or floating, 1.8 to 2.7 m away, with sideways shifts); only when no such place exists does the search fall back to any sofa that fits, so a living room never loses its sofa. Wardrobes, bookcases and shelving units get a bonus of 3 m of free wall (`TALL_WALL_BONUS`) on north and west walls (`onNorthOrWestWall`), which keeps them from standing between the default camera and the room; the option `tallPrefer: false` switches the bonus off. A studio (a living room named studio, garsoniera or kawalerka, see `isStudio` in `rooms.js`) also gets a `sleep` zone: `sleepRecipe` puts a bed along a wall away from the sofa, with nightstands and lamps when they fit, and steps down to a smaller bed and then to a sofa bed when the room is tight; a room that already holds a bed or a sofa bed is left as it is.

A prop layer (`decorate` in `recipes.js`) runs after all rooms have their furniture and fills what is left, in this order: pictures and curtains from the plan (`hangArt`, `hangCurtains`); small things on furniture (`dressTops`: a vase, a small plant, a stack of books or a centrepiece on a sideboard, chest of drawers, television unit, desk, coffee table and dining table, two to four per room by its area, at fixed offsets across the top that `R.on` refuses when a lamp or plant already stands there); more pictures in proportion to the free wall of the room, at most five in a living room and four elsewhere, and a mirror in bedrooms and in living rooms of 16 m2 or more (`hangMore`; each goes on the stretch of free wall with the widest gap to its wall-mounted neighbours, at least 0.35 m, and the engine's usual test keeps it off windows, door zones and tall furniture); a second and third large plant in free corners of rooms of 12 and 22 m2 (`morePlants`); a rug under the dining table and a runner along a hall when the door zones leave room for one (`moreRugs`). Everything goes through `R.on`, `R.alongEdge` and `R.corner`, so the rules of the layout hold unchanged. On the fourteen test plans (`seed` 7, every built type allowed) the layer takes pictures from 99 to 153, mirrors from 16 to 30, plants from 42 to 59 and small things on furniture from 0 to 39, and the pieces from 726 to 851, with no violation on any plan. The small things and the hall runner belong to the extended catalogue, so the default type set of the engine gets only the pictures, mirrors, plants and the dining rug. `fillFloor` looks at the floor itself: on a grid of 0.2 m cells it finds the biggest connected stretch (at least 1.6 m2, 0.15 m from the walls) that is further than 0.8 m from every piece standing on the floor, puts a rug there (a smaller one when the first does not fit) and an armchair facing its middle with a small round table beside it; a hall or landing of 10 m2 or more only gets the rug. Every placement goes through `R.at`, so the rules above hold unchanged, and a stretch that the rules keep free on purpose (a door swing, the clear front of a television) stays free.

## 5a. Editor (src/editor)

Pure functions, no DOM, no three.js, no storage and no network. They run in Node and in the page; the page keeps one state and replaces it with the state an operation returns. `src/editor/index.js` is the public API. `resetToAuto` runs the engine of section 5 again, prop layer included, so the pictures, plants and small things it adds are ordinary pieces of the layout document.

**State.** `{ layout, selection, history }`: `layout` is the document of section 3, `selection` is a piece id or null, `history` is `{ past, future, key }` (layouts, at most 200 steps). Updates are immutable: an operation builds a new state that shares every unchanged piece with the old one and never touches its input. Treat piece objects as read-only (their boxes are cached per object).

**Operations.** Every operation returns `{ state, ok, reason?, problems? }`, never throws, and hands back the input state itself when it fails. Reasons: `bad-state`, `unknown-id`, `unknown-type`, `unknown-level`, `bad-number`, `bad-slot`, `bad-color`, `bad-part`, `unknown-room`, `no-change`, `fixed-size`, `no-room`, `limit-level`, `limit-total`, `limit-rooms`, `nothing-to-undo`, `nothing-to-redo`, plus the hard problems of strict mode (below).

| call | effect |
| --- | --- |
| `createState(layout)` | fresh state with an empty history (anything that is not a layout becomes an empty one) |
| `addPiece(state, { type, x, y, rot?, level?, room?, size?, colors?, elev? }, opts)` | new piece with a fresh id (`p<n>`), spec size clamped to `range`, mounting height from `place`, selected; a prop finds the piece under it |
| `movePiece(state, id, x, y, opts)` | moves the centre; what stands on the piece comes along; the room follows the centre |
| `rotatePiece(state, id, deg, opts)` / `turnPiece(state, id, delta, opts)` | new angle / angle change in degrees clockwise; what stands on the piece turns around its centre |
| `deletePiece(state, id)` | removes the piece and everything that stands on it (one undo step brings all back) |
| `resizePiece(state, id, size, opts)` | `size` is `[w, d, h]` or a partial `{ w, d, h }`, clamped to `range`; an axis without a range is fixed; the footprint grows around the centre, except that a piece standing with its back on a wall (within 3 cm of the usual gap) keeps its back there when the depth changes (`snapped.wall`); props on top follow |
| `duplicatePiece(state, id, opts)` | a copy 0.3 m to the right of the piece and 0.3 m in front of it (in the piece's own directions), snapped and checked like `addPiece`, new id, selected, own copy of the colours; what stands on the piece is not copied; one undo step |
| `recolorPiece(state, id, slot, color, opts)` | `color` is `#rrggbb` (stored lower case), `lib:<key>`, `f:<key>` or `null` for the default; a bare library key is stored as `lib:<key>` |
| `recolorRoom(state, level, room, part, color, opts)` | `part` is `'wall'` or `'floor'`; `color` is `#rrggbb` or `lib:<key>` (no `f:`), `null` clears the part (the last part removes the room entry, and the level's `rooms` key when it is empty); with `opts.model` the room must be on that level of the plan; one undo step, a series with the same `coalesceKey` is one step; `roomColorsOf(layout, level, room)` reads the colours back |
| `resetToAuto(state, model, { seed?, allowedTypes? })` | the layout engine furnishes the plan again; the result has no room colours, so they are cleared too (one undo step brings pieces and colours back, selection cleared) |
| `loadLayout(state, layout)` | replaces the layout (a loaded file), one undo step |
| `selectPiece(state, id \| null)`, `selectedPiece`, `findPiece`, `pieceAt(layout, level, x, y)` | selection and picking (the topmost piece under a point) |
| `undo(state)`, `redo(state)`, `canUndo`, `canRedo` | history; a new operation clears the redo list |

Options of the placing operations: `model` (the built plan; without it only overlaps and props are checked), `mode` (`soft`: snap and report problems, accept; `strict`: also refuse hard problems; `off`: no snapping and no checks), `snap` (`false`, or overrides for `grid`, `angle`, `wallGap`, `wallReach`, `wallAngle`, and `edges`), `coalesceKey`. Operations that carry the same `coalesceKey` in a row share one undo step (one drag of one piece); another key, no key, an undo or a redo ends the series.

**Rules** (`rules.js`). Snapping, in this order: the angle to 15 degrees (a move keeps the angle), the position to a 5 cm grid, and then, for pieces that stand with their back to a wall (`place.against` back or back-or-free, wall-mounted and window pieces), the back to the nearest wall of the room within 20 cm when the piece is turned at most 20 degrees from facing away from that wall: the gap becomes 2 cm (4 mm for wall-mounted pieces) and the angle becomes the wall's. With `snap: { edges: true }` (off by default) a floor piece also pulls a side to the side of a neighbour in the same room that is closer than `edgeReach` (15 cm), when both are turned the same way modulo 90 degrees and overlap along the shared side: the gap becomes `edgeGap` (5 mm); this runs before the wall step, so the wall keeps the last word along its normal. Positions stay within `COORD_LIMIT` (1000 m) and heights within 0 to `ELEV_LIMIT` (10 m), the limits the file reader applies. Results are rounded to the millimetre. `placementProblems(model, layout, level, piece)` lists `{ kind, with? }`:

- `outside-room`: the footprint is not inside the room's floor polygon.
- `overlap`: another piece blocks it (turned rectangles, heights, props and rugs follow the engine's `blocks` rule).
- `door-zone`, `stair`: inside the zones of `levelZones` (0.8 m in front of and behind each door plus the swing; stairs with a margin).
- `tall-before-window`: a tall or wall-mounted piece in front of a window.
- `floating-prop`: a prop (`place.mode` surface or `on` set) whose support is missing, of the wrong type, at the wrong height or too far from the centre.
- `front-blocked` (soft): the strip in front of a floor piece (`place.clearFront` deep, 90% of its width, see `clearBox`) reaches another solid piece of the same room (`with` says which) or the wall (no `with`); pieces that belong there do not count (a coffee table in front of a sofa, an armchair or the television unit, a seat in front of the television unit, a desk chair at its desk; kitchen units and bathroom fixtures do not block each other, because the fronts of an L or U shaped run and of the fixtures of a small bathroom share the open floor). The layout engine uses the same strip when it places pieces; `checkLayout` does not report it, so the editor and the checker differ here on purpose.

`strict` mode refuses `overlap`, `outside-room` and `floating-prop` (`HARD_KINDS`); the other kinds (door zone, stair, tall piece at a window, blocked front) are warnings in every mode. A prop moved onto another piece that accepts it changes its `on` and `elev`; dropped on bare floor it has no support.

**Colours** (`colors.js`, a pure module). One spelling everywhere a colour is stored: `#rrggbb`, `lib:<key>` (a key of `MATERIAL_KEYS`) and, for piece slots only, `f:<key>` (one of `FURNITURE_COLOR_KEYS`, a copy of the `f:` materials of the kit; a test keeps the copy equal to the kit). `readColor(value, kind, keys?)` gives `{ value, bare }` or `null` (`kind` is `'piece'` or `'room'`), `cleanColor(value, keys?)` and `cleanRoomColor(value, keys?)` give the full form or `null`. A bare library key is accepted as `lib:<key>` (`bare: true`) so that older files and callers still work, and the file reader says so in a warning; nothing is ever written in the short form. Every value the editor accepts for a piece is accepted by the piece builder (`isSlotColor`), and every colour of `PALETTES` and `ROOM_PALETTES` is valid here.

**Rooms** (`rules.js`). `roomAt(model, level, x, y, prefer?)` gives the id of the room whose floor holds the point, or `null`. `roomsOf(model, level)` lists the rooms of a level in plan order as `{ id, name, use, area, polygon, interior }` (`polygon` as drawn in the plan, `interior` the floor inside the walls, `null` when there is none; copies, at most 400). `roomInfoAt(model, level, x, y, prefer?)` gives that record for the room under a point, or `null`. A page can pick a room by the floor under a finger with these and colour it with `recolorRoom`.

**Saving and loading** (`io.js`). `serializeLayout(layout)` gives JSON text with a fixed key order, sorted colour slots and one piece per line (or `null` for something that is not a layout); the same layout always gives the same text. `parseLayout(text, model?, { strict? })` returns `{ ok, layout, errors, warnings }`. Errors make the file unusable: not text, more than 2 000 000 characters, not JSON, version other than 1, no list of levels, more than 20 levels, more than 400 pieces on a level or 1500 in all. Warnings list what was repaired or left out, at most 60 of them (the last one says how many more there were): sizes moved into their range, unknown colour slots and invalid colours, heights of props moved onto their support, duplicate ids, unknown types, non-finite numbers, supports that are missing, of the wrong type or part of a loop, and (with a model) levels, rooms or pieces that are not in the plan. With `strict` any warning counts as an error. Only the known keys of a piece are read, so keys such as `__proto__` cannot reach the result. Room colours (`levels[].rooms`) are written sorted by room id, `wall` before `floor`, and a level without colours has no `rooms` key, so older files and newer files without colours have the same text. When reading, only `wall` and `floor` are taken, a colour must be `#rrggbb` or `lib:<key>` (a room) or also `f:<key>` (a piece slot), a bare library key is read as `lib:<key>` with a warning, with a plan the room must exist on that level, at most 200 rooms are read per level, and `__proto__`, `constructor` and `prototype` are refused as room ids; whatever is left out gets a warning.

**Files** (`src/app/files.js`, the only code that saves and reads files). `saveTextFile(doc, filename, text)` offers text as a download through a temporary hidden link (`application/json`) and returns `true`, or `false` when the browser lacks the API or the text is empty. Download addresses are released 10 seconds after the click (`REVOKE_DELAY_MS`; at once when the click failed). `readTextFile(doc)` opens the file picker (one at a time: an older, unanswered picker is closed first, and so is one whose window got the focus back without a file) and resolves to `{ ok: true, text }` or `{ ok: false, error }` with `cancelled`, `read-failed`, `too-large` (over `MAX_PLAN_CHARS`, 2 million characters, the one size limit of `src/core/limits.js`) or `unsupported`. `askForText(doc, lang)` shows a small dialog (Polish or English) for pasting text and resolves to the text or `null` when cancelled; an empty or too long text keeps the dialog open and says why. Plan problems reach the page as one line: in Polish a short sentence per validator code (`PL_ERRORS` in `src/app/planfile.js`), with the validator's own English sentence as the hover text. The layout file is called `plandoll-layout.json` (`LAYOUT_FILENAME`). Nothing is kept in the browser and nothing is sent anywhere.

## 6. Look (src/look, src/app)

The look module owns the stage (sky, light rig, backdrop, base), the time-of-day keyframes, the post-processing chain and the quality levels. The app shell owns the page: canvas, the three presets (`amber`, `clear`, `lamplit`), the time slider, the quality switch, the error card when WebGL2 is missing.

Lamps: every lamp point light reaches `LAMP_RANGE` (5.5 m, smooth cut-off) and the bloom pass only takes pixels above `BLOOM_THRESHOLD`, so a shade keeps its shape and a lamp lights a pool instead of the whole room. At night the base under the model darkens with the lamps (`stage.applyTime`).

The `plan` parameter takes `flat-1` or `duplex-1`. `ext` shows a plan injected as `window.__plan` before the page loads (the screenshot tool does this with `--plan FILE`). Any other value, including `gen:<seed>`, shows `flat-1`: plans are generated by a Node tool (`tools/gen-plans.mjs`), not in the browser.

## 6a. Camera (src/app/camera.js, src/render/cutaway.js)

The model can be turned round and looked at from every side. `src/app/camera.js` has two parts.

- The pure part keeps the view as `{ azimuth, polar, distance, base }` (degrees and metres) round a target: `orbit`, `zoom`, `positionOf`, `stateFrom`, `blend`, `rayFor`. Azimuth 0 looks from the south, 90 from the east, 180 from the north, 270 from the west. The polar angle stays between 12 and 80 degrees from the vertical (never under the table, never straight down) and the distance between 0.2 and 1.8 times the default (`ZOOM_MIN`, `ZOOM_MAX`). The pan is not part of that state: it is an offset `[x, z]` in metres of the target over the ground plane (the height of the target never changes), held by the controller and added to the home target.
- The pure helpers for pan and zoom at a point take picture coordinates (x, y in -1..1, up positive, as `rayFor` does): `groundPoint(state, target, fov, aspect, x, y)` is where the ray through a picture point meets the horizontal plane at the height of the target (null near the horizon); `toPicture(rect, clientX, clientY, lift)` converts a client point, with the picture point (0, 0) at the centre of the projection, which `lift` (picture units, `liftOf(cover)`, at most `BOTTOM_MAX` 0.4) moves up over the middle of the part above the bars: the page fits the model with `fitView(..., { bottom: cover, lift: true })`, so the target is the middle of the model and the model is centred in the free part, and moves the projection of the three.js camera by the same amount (`setViewOffset`), instead of aiming the camera at a point far below the floor, which made turning and zooming swing the model out of the picture; the controller takes `lift` (and `setLift`) for every conversion, `pointerToRay` and `groundAt`; `panShift(before, after, target, fov, aspect, from, to)` is the shift of the target that puts the ground point that `before` showed at `from` at `to` once the view is `after`, which is the one rule behind every gesture (a pinch is a zoom plus a shift, the middle of the fingers is `from` and `to`); `panByPixels` is the plain drag; `zoomAt` zooms about a point and returns the zoomed state and the shift; `panLimits(box, grow)` grows a box by `grow` of its size on every side (`PAN_GROW` 0.15 for the open extent without the shell; with the shell the page gives the card board of the moment and 0.04, so a pinch or a drag over the empty ground cannot lose the model, and `setLimits` is called on every step of the shell so that a shrinking board brings the view back) and `clampPan` keeps home plus pan inside it (a pan of zero is always allowed); `blendPan` eases the pan back in the reset; `nearPlane(distance)` is 4 percent of the distance between 0.12 and 0.5 m, which the page sets on the camera so that a close view does not cut the model (the starting view keeps 0.5 m).
- `createCameraController` listens to pointers on the canvas. Touch: one finger turns (with a short inertia after a flick); two fingers zoom about the point between them and move with their middle at the same time, so the ground under the fingers stays under them; three or more fingers move with their middle and never zoom. Mouse: the left button turns; the right button, the middle button, or Shift with the left button, move (the context menu is suppressed over the picture); the wheel (and a trackpad pinch, which arrives as Ctrl and wheel) zooms towards the pointer. When a finger goes down or up the reference of the gesture is taken again, so nothing jumps. The finger that is left after the others lift does nothing until it lifts too (`gesture.multi`), a finger that goes down as the first of its kind drops any pointer kept from before (a missed pointerup), the window losing the focus or the page going to the background drops them all, a touch may wander `SLOP_TOUCH` (10 px) and still be a tap (the mouse `SLOP_MOUSE`, 6 px), and two fingers closer than `PINCH_MIN` (24 px) only jitter and do not zoom. A double tap or double click goes back to the starting view in 400 ms, the pan included (the reset eases the pan to zero with the turn and the zoom). `options.limits` (the open extent) limits the pan, `setLimits` changes it, `setTarget` and `rehome` keep the pan, now from the new home, so framing again after a resize keeps what the person did. `target` is the effective target (home plus pan) and `homeTarget` the home one; `groundAt(clientX, clientY)` gives the ground point under a client point. `onGesture({ kind, pointerType })` reports `orbit`, `pinch`, `pan`, `wheel` or `key`: the page shows its one-line touch hint (Polish and English, in the message line of the control bar, 6 seconds, once per page load, nothing stored) at the first one-finger turn by touch. Arrow keys turn by 15 degrees (Shift + left or right still moves the time of day), `+` and `-` zoom, `0` resets. It asks the page for a frame only while something moves (a short inertia after a flick, the reset animation), so an idle page draws nothing. `enabled` switches it off (an editor does that while a piece is dragged) and `pointerToRay(event)` gives the ray under a pointer for picking.

`nearSides(azimuth, previous)` says which edges of the plan face the camera, with 10 degrees of hysteresis so a wall on the turning point does not flicker. Only when that set changes does the page cut the walls again: `applyWallCut` (`src/render/cutaway.js`) cuts the outer walls on a near edge low and leaves the other outer walls tall, partitions stay at half height; `cutawayPieces(pieces, ext, view, near)` hides the hung and tall pieces the new cut would spoil; then the merged meshes, the shadow casters and the lamp emitters are rebuilt. A full-height wall on the south or east edge does not cast a sun shadow (the sun stands on that side), so a view from the north does not drown the rooms. The same set of near edges cuts the upper storey of a duplex. The default view is the picture the page had before it could be turned.

The address takes `az` and `pol` (degrees) for the view the page opens with, for example `#amber&az=90` looks from the east. When that view differs from the default by more than a degree, the distance and the target are fitted to the model as it looks from there: `fitView(state, bounds, { fov, aspect, margin, bottom, lift })` projects the eight corners of the box round all storeys, takes the smallest distance at which they all fit with the margin (8 percent) and moves the target so that the projected box is centred; the fitted view becomes the home view of the controller (`setTarget` moves the target of the controller, `initial.distance` starts at another distance) and is refitted when the window changes shape. While the open shell is on (the default) the view is always fitted, to the points of the closed model and of every wall lying flat (`fitView` takes them as `points`, see 6c), and the bars are kept clear of the model on a wide window too. `bottom` (0 to 0.4) is the share of the picture height, from the bottom edge, that bars cover: the box is then fitted into the part above them. Without `lift` that is done by aiming the target below the box so that the box rises on the picture (the target then lies far below the floor on a phone, and turning or zooming swings the model round a point behind the controls); with `lift: true`, which the page passes for every fitted view, the target stays in the middle of the box, the box is centred in the free part and the page moves the centre of the projection of its camera up by the same share (`liftOf(cover)`, `camera.setViewOffset`), so everything turns and zooms about what the person sees. On a narrow window (up to `NARROW_WIDTH`, 760 px, where the bars span the window) the page measures the controls and, while editing, the edit bar (`#ps-ui`, `#ps-edit`; the sheet of the panel is left out, so the view does not jump when it folds or hides while a piece is dragged) with `coverShare` in `src/app/stack.js`, passes the share to `fitView`, and frames again when the window or the bars change size. The default view (azimuth 36, the polar angle from `cameraFor`) is left as it is while `lowestOnPicture` says that the lowest corner of the box shows above the bars; when it would sit behind them (a tall model on a phone) the view is fitted into the part above them from the same side and tilt (with the lift, like every fitted view; a default view that already shows the whole box has no lift). Picking is not affected: the camera moves its target and its distance, and `pointerToRay` uses the effective target (home plus pan), so it stays exact while the picture is moved. The editor leaves a second or third finger, the right and middle buttons and Shift with the left button to the camera: a gesture of two or three fingers that starts on a piece puts the piece back, takes back the selection the first finger made and moves no piece. A wider window (the bars are a small box in the middle) and a picture of another size than the window (a captured frame) are framed without bars, as before.

For test tools the page has `window.__camera` (`azimuth`, `polar`, `distance`, `base`, `pan`, `target`, `nearPlane`, `groundAt(clientX, clientY)`, `set`, `reset`). `tools/interact.mjs --btn` drives real touch and mouse events through the browser's own input pipeline on a phone and on a desktop window, on the flat and on the duplex: two fingers that move together, a pinch about a point, three fingers, a long drag to the limit, the right and middle button, Shift with the left button, the wheel at the pointer, the nearest zoom, the double tap and the double click, a change of the window size, and the touch hint; each step checks that the picture changed, that the ground point under the fingers (`groundAt`) did not drift, and that nothing was logged, stored or requested. `--edit` does the same for gestures that start on a piece (no piece moves, nothing is selected).

Frame hook for screenshots and video capture. `window.__frame({ preset, t, az, pol, dist, size })` returns a promise of `{ frames, drawCalls }`. It sets the mood (`amber`, `clear`, `lamplit`), the time of day `t` (0 to 1), the view (`az` and `pol` in degrees, `dist` as a multiple of the default distance, 0.2 to 1.8) and the size of the picture (`size: { w, h }`, 320 to 3840 by 180 to 2160 pixels), asks for exactly one new frame, and resolves after the animation frame in which that frame was drawn, so a capture right after it sees the finished picture. Every field is optional; a value that is not a finite number or an unknown mood is dropped and a number out of range is clamped (`src/app/capture.js`, tested in Node). The hook changes nothing while nobody calls it, writes nothing to the browser and makes no request.

## 6b. Edit mode (src/app/edit.js, src/app/pick.js, src/render/outline.js)

The address parameter `edit=1` turns the layout editor on. It is off by default: without it the page draws the same calls and the same picture as before and has no edit bar and no pointer handling for editing. The pieces stay merged by material as on the plain page (`mergeByMaterial(furn, skip)` in `src/render/compose.js`), except the piece that is being dragged: at the first move it leaves the merged meshes (`live` in `src/app/main.js`, the meshes are rebuilt once) and at the end of the drag, on a cancelled drag, a turn or an undo every piece goes back in (`merge=0` turns merging off, and then the pieces are single objects). While merged, the group of a piece is hidden; picking skips only the pieces that the cutaway hid (`furn.cutHidden`; a piece that hangs on a turned wall stays an object of its own and its own `visible` flag counts). With the shell open the piece that is dragged and the pieces hung on the walls are the objects that stay out of the merged meshes. The draw call limits of the plain view (1800 on high, 700 on low) hold in edit mode too.

- **Session** (`src/app/edit.js`, pure logic, tested in Node on the example plans). `createEditSession({ layout, model, onChange, allowedTypes })` holds the state of `src/editor` and forwards the operations of the interface to it: `select`, `add(type, at)`, `turn(deg)`, `remove`, `resize`, `recolor`, `undo`, `redo`, `reset` (automatic layout), `exportText`, `importText`, and for dragging `beginDrag(id)`, `dragTo(x, y)`, `endDrag`, `cancelDrag`. Placement is always in the `soft` mode of the editor: a piece accepts every place after snapping, the outline shows what is wrong, Undo is always at hand. `add` looks for the best free place of the room under the centre of the view (candidate points ordered by distance, four angles each, the first without overlap, door zone, stair or unsupported prop wins; when there is none the piece goes to the middle of the room with its problems shown). `onChange({ type })` says what the page has to redraw: `structure` (pieces added, removed, resized, recoloured, or places changed by turn, undo, redo, reset, import), `drag` (move only the group of the dragged piece), `dragend` (then refresh lamps and shadow casters) and `select`.
- **Picking** (`src/app/pick.js`). `pickPiece(layout, ray, { levelBase, skip, pad, frameOf })` tests the ray against the oriented boxes of the pieces (centre, angle, size, height from `elev` to `elev + h` above the floor of the level) and returns the nearest `{ id, level, t, point }` in front of the camera; `skip(id)` leaves out pieces that the wall cutaway hides. It does not use the meshes, which are merged by material in the normal view. `frameOf(id)` gives the 4 x 4 matrix (column-major) that carries a piece from its place in the layout to where it is drawn, or null: a piece that hangs on an outer wall which has turned (shell open) is drawn at the hinge matrix of its wall, so its box is tested with the ray taken back through that matrix (`rayInFrame`; the matrix keeps lengths, so `t` is comparable between pieces in different frames, and `point` is a point of the original ray). `floorHit(ray, y)` meets the ray with a horizontal plane (the base of the dragged piece) and `planeHit(ray, point, normal)` with any plane.
- **Gestures** (`src/app/main.js`). A pointer that goes down on a piece selects it and switches the camera off for the length of the gesture; after 6 px of movement the piece is dragged (the grab offset is kept), each move calls `floorHit` at the height of the piece's foot and `session.dragTo`, which snaps (5 cm grid, walls) and moves the piece with what stands on it; only the groups of the pieces are moved and the outline follows, nothing is rebuilt. With the shell open a piece that hangs on a fallen wall is not dragged over the floor plane: `slidePoint(ray, host, height)` in `src/app/pick.js` takes the ray back through the hinge matrix of its wall (`shell.hostOf(id)`) and meets the inner face of the wall in the wall's closed place (`innerFace` in `src/model/foldwalls.js`), so the piece slides along its wall under the finger wherever the wall lies, and keeps its place on the wall; if another wall holds the piece than at the grab (the shell opened or closed meanwhile) the drag waits. Releasing keeps the place as one undo step; `pointercancel`, or a second finger during the drag, puts the piece back and returns the camera. A drag that starts on an empty place is the camera as before; a quick tap on nothing clears the selection. Keys (not while a form field has the focus): Delete or Backspace removes, R turns by 90 degrees, Ctrl or Cmd + Z undoes, Ctrl or Cmd + Shift + Z and Ctrl + Y redo, Escape clears the selection and takes that key press (`preventDefault`), so with the shell open it stays open; `shellKey` ignores a key press that something already took, and the next Escape, with nothing selected, folds the shell.
- **Re-composing.** After a `structure` change the page compares a signature (type, size, colours) of each piece with the one it built; when only places changed the groups are moved (`position`, `rotation.y`) and the cutaway, lamps and shadow casters are refreshed, otherwise the furniture is composed again. The selection is kept by id.
- **Outline** (`src/render/outline.js`). A tinted rectangle with a rim on the floor under the piece plus the twelve edges of its box as thin bars, each over a wider dark bar so that the outline reads on light and on dark furniture; drawn last without a depth test. Red for `overlap`, `outside-room` and `floating-prop`, yellow for the other problems (`door-zone`, `stair`, `tall-before-window`, `front-blocked`), light copper when the place is fine. `createOutlineFrame(outline)` holds the outline's group in a frame group with its own matrix: `follow(matrix)` gives it the hinge matrix of the wall that holds the selected piece, so the outline of a piece on a fallen wall turns with the piece (the page calls it when the selection or the layout changes and on every step of the shell's motion), `follow(null)` puts it back. `createRoomOutline()` draws the floor outline of a selected room (tinted fill, thick light rim over a dark one, any simple polygon).
- **Rooms** (`src/app/edit.js`). `selectRoom(levelId, roomId | null)`, `selectedRoom()` (`{ level, id, name, colors: { wall?, floor? } }` or null) and `recolorRoom(part, color | null)` (`part` is `'wall'` or `'floor'`, colour `#rrggbb` or `lib:<key>`, a run of changes of one part is one undo step). A piece and a room are never selected together. A quick tap on a floor where no piece stands selects the room under the finger (the ray meets the floor of the highest storey first); a tap beside the plan or Escape clears it. After every structural change the page gives the colours of all rooms to `PlanScene.setRoomColors(colors, look)` when the scene has that method; a plan without any room colour is drawn exactly as before.
- **Duplicate and edge snapping.** `duplicate()` copies the selected piece (the copy is selected, one undo step). `setSnapEdges(on)` and `snapEdges()` switch the snapping of a dragged piece to the sides of its neighbours (off by default). `createEditSession({ viewPoint })` gives `add` the plan point and storey under the centre of the picture above the bars; a given place wins.
- **Edit bar** (`createEditBar` in `src/app/ui.js`). Rotate piece, Delete, Undo, Redo, Reset layout and File (Polish: Obróć mebel, Usuń, Cofnij, Ponów, Układ od nowa, Plik), each at least 44 px, with text on two lines when needed, disabled when there is nothing to do, one row above the controls (six equal columns on a 390 px phone). A one-time hint above the bar (tap a piece to select it, drag to move it) goes away at the first selection. File opens a small menu above the bar with Duplicate piece, Save layout, Load from file, Paste layout, Save image and Load plan; a tap outside the bar or Escape closes it. `say(text)` shows one short line above the bar for a few seconds (the result of a load: loaded, how many items were skipped, or why nothing was loaded). The height of the stack at the bottom (bar, mood caption, controls) is published as `--ps-stack-h` on the root element. `#ps-edit-panel` is an empty container for further panels.
- **Panel and files.** With the controls on, `createPanel` (`src/app/panel.js`) is created next to the bar: the list of furniture to add, the size fields and the colour swatches of the selected piece; it is hidden while a piece is dragged. Save uses `saveTextFile(document, LAYOUT_FILENAME, session.exportText())`, Load from file `readTextFile`, Paste layout `askForText`; the text goes to `session.importText`.
- **Extra buttons (on by default, `btn=0` hides them).** The control bar has a row with the example plans, Open the shell, Edit, Save image and Load plan (at least 44 px, wrapping inside the bar on a 390 px phone, on its own line on a wide window); in the editor the row holds Done and the shell button, which works as it does outside the editor (the example plans, Save image and Load plan leave it). `createUI` also has `say(text)`, one short result line above the bar for the plain page (the edit bar has its own). Edit reloads the page with `edit=1` added to the address (`editHash` in `src/app/params.js` keeps the other parameters and writes the current mood, time of day, quality and language into the address), and in the editor the same button reads Done and reloads without it. The address follows the layout (see the share link below), so Done awaits the last write and leaves on the first tap. Only two cases show a line in the result line of the edit bar first, and then the second tap leaves (`leaveAdvice` in `src/app/addrsync.js`): the address could not take the layout (too large, or a browser that refuses the change; Save layout in the File menu is the way out, and the second tap tries the address once more), and pieces whose centre stands outside every room (the reader of a link leaves them out, so they would be gone after Done; the line gives their number). Save image draws the current view once more and hands the canvas over as `plandoll-view.png` (`toBlob`, then `saveBlobFile` in `src/app/files.js`); the same action is in the File menu of the edit bar. Load plan (`loadPlan` and `applyPlan` in `src/app/main.js`): `askForText(document, lang, { kind: 'plan' })` shows the box (a field and a button that fills it from a file), `readPlanText` (`src/app/planfile.js`) validates, then everything new is built first (model, scene, automatic layout) so that a plan that cannot be built changes nothing; then the old furniture, scene and stage are disposed, the stage, the walls, the pieces and the default view are made again, and in edit mode a new session (no undo history) and a new panel replace the old ones. `window.__planInfo()` gives `{ pieces, levels, rooms, extent }` to test tools.
- **Dragging details.** The margin of the pick box is 2 cm for a mouse and 6 cm for a touch. While a piece is dragged the plane that the finger points at follows the piece's height, so a prop that leaves a table stays under the finger. A second finger puts the piece back, takes back the selection that the first finger made (the piece that was selected before, or the room that was picked before: `selectionNow` and `restoreSelection` of the session) and hands both fingers to the camera, so the pinch starts at once. The click of a touch tap goes to whatever is under the finger when it lifts, and the selection that a tap makes opens the sheet of the panel over the picture, perhaps under the finger: a click that follows the lift of a touch or pen pointer that went down on the picture, within 500 ms and 24 px of where it lifted, and is not for the picture itself, is dropped (`strayClick` in `src/app/shell.js`, a listener in the capture phase in `main.js`), so a tap that selects a piece cannot recolour it through a swatch that appeared under the finger. A mouse holds the pointer on the picture for the click too and is not affected. Escape in the Add list of the panel closes the list and goes no further.
- **For test tools.** `window.__edit = { session, screenOf(id), floorAt(x, y, levelId), pointOf(levelId, x, z), count(), selectedId(), selectedRoomId(), roomHit(x, y), freeFloor(levelId, roomId), hit(x, y), canPlace(id, x, z), outlineGap(id), own(id), hostOf(id), alongWall(id, d) }` (`screenOf` finds the piece where it is drawn now, also on a fallen wall; `outlineGap(id)` is the largest distance in pixels between the corners of the piece's box as drawn and the same corners of the selection outline, `own(id)` says whether the piece is drawn as an object of its own, `hostOf(id)` names the turned wall that holds it, `alongWall(id, d)` is the client point `d` metres along that wall from the piece; `floorAt` gives the plan point under a client point, `pointOf` the client point of a plan point, so a test can drop a piece exactly on another; `canPlace(id, x, z)` says without changing anything and without a drag whether the piece would stand clean at a plan point of its level, as `{ ok, problems }` from the editor rules: overlap, outside the room, door zone, stair and floating prop count against it); `tools/interact.mjs --edit` taps a piece at `screenOf(id)`, drags it by about 80 px, turns, undoes, redoes, deletes and restores the automatic layout, opens the panel and adds a piece from the list, recolours it with a swatch, changes a size field, duplicates from the File menu, saves (the blob handed to `URL.createObjectURL` starts with `{` and equals the exported text), loads the saved text through the paste dialog, picks a room by a tap on the floor and recolours it, and checks after each step that the layout and the picture changed and that Undo takes the change back.

## 6c. Open the shell (src/model/foldwalls.js, src/render/openmotion.js, src/render/openshell.js)

The control bar has a button, Open the shell (Polish: Otwórz bryłę), and the outer walls (`kind: exterior`) fall outward round the foot line of their outer face and lie flat, inner face up, with their windows, doors and hung pieces; a second tap, Space or Escape folds them back. `#shell=0` takes the button away: no hinge groups, and the view is framed for the closed model alone, as before the shell existed. The shell is built whenever its button is on (`shellOn` in `src/app/shell.js`: only `shell=0` turns it off), also while the editor is on (`edit=1`), and the editor works with the walls down. Moving, turning, deleting, undo and redo, colours, sizes, adding pieces, the panel and loading a plan do not care where the walls are. Three things needed care because a piece hung on an outer wall turns with its wall: picking and dragging take the ray back through the hinge matrix of the wall (section 6b, Picking and Gestures), the selection outline rides in a frame that carries the same matrix (`createOutlineFrame`), and Escape belongs to the editor first (it clears the selection and takes the key press) and to the shell second. The Edit button still reloads the page, which starts with the walls up. Known limit of the shell: a plan with a concave outer corner (an L-shaped house) lays two walls partly on top of each other in one plane, and a wall can land on a balcony; the two example plans are clean.

- **Geometry** (`src/model/foldwalls.js`, pure). `foldWalls(model)` lists the outer walls with the outward normal (the side without rooms), the hinge line (the outer face, at the foot of the wall's boxes) and how far the top lies once the wall is flat; `hingeMatrix(f, deg)` is the 4 x 4 turn about that line; `openExtent(model, ext)` is the box of the closed model together with every wall lying flat (the stage frames it) and `openPoints(model, ext)` the corners of the closed model and of every wall lying flat (the camera fits these, a tighter fit than the box), both once, so the view stays put while the walls move; `hostWall` names the outer wall that a hung piece hangs on.
- **Motion** (`src/render/openmotion.js`, pure). One clock p (0 closed, 1 open) runs forward to open and backward to close, so closing is the same motion in reverse; the whole motion takes 3 s. Every wall has its own time, worked out from p and its rank (the walls that face the camera start first, 80 to 150 ms apart): a cubic ease-out to 94 degrees, then back to exactly 90. A wall that the cutaway holds low in the closed view rises to full height in the first 40 percent of its own time.
- **Scene** (`src/render/openshell.js`). `createOpenShell(ps, model)` takes the existing group of every outer wall and of its openings (`wall:<id>`, `opening:<id>`), switches off their automatic matrix and sets the hinge matrix, so the boxes inside keep their positions and `applyWallCut(ps, ext, near, { height })` keeps working on them (`heightFor` lifts the cut of the walls that fall). `adopt` moves the pieces hung on those walls into hinge groups of their own (they are not merged while the shell is not closed) and shows each one once its wall has risen above its lower edge. `hostMatrix(id)` gives the matrix of the hinge group that holds a piece (or null) and `hostOf(id)` also names the wall and gives its inner face plane, for picking, dragging and the outline of the editor. The window light patches on the floor are switched off while the shell is not closed.
- **Page** (`src/app/main.js`). The clock runs on `requestAnimationFrame` only while the shell moves; each step poses the walls, cuts them for the view and asks for a frame; the furniture and the shadow casters are settled when the shell leaves or reaches the closed state. The camera is not touched. `window.__shell` (`seek(p)`, `open()`, `close()`, `state()`, `view()`, `extent()`, `project()`, `shadow()`; present when the shell is built, also while editing) is for test tools and for filming; Space opens or closes (`shellKey` in `src/app/shell.js`), Escape closes (while editing, the first Escape clears a selection and the shell stays open).

- **Card board** (`src/look/board.js`, pure; `setBoard` in `src/look/stage.js`). The board under the model, its darker under-board and the contact shadow are one rectangle that follows the walls. `boardRect(ext, walls, degs)` takes the closed extent, the fold walls and the angle of each wall (`shell.state()`): a wall that has turned by `deg` degrees reaches `reach * sin(deg)` out of its outer face, so the extent is that of the walls as they stand, never a wall off the board. Closed, the rim beyond the outer faces is max(0.35 m, 6 percent of the larger side); flat, it is max(0.3 m, 3 percent of the larger side) round the open extent; in between it eases by how far the walls have fallen. The page calls `stage.setBoard` in every step of the shell tick and of `seek`, so the board grows with the opening and shrinks back when the shell folds, in a new plan too (`applyPlan`). The lights and the pool of tabletop keep the bounds of the open extent, and the starting view is untouched. Without the shell (`shell=0`) or on a plan with no outer wall that opens, the board is the bounds with a margin of 9 percent as before. Editing (`edit=1`) does not change this: the shell is built while editing too, so an edited house has the board that hugs the closed house and grows with the opening shell. `window.__stats.board` (a getter) gives the board now, `{ minX, maxX, minZ, maxZ, width, depth }` in metres, to test tools.

## 6d. Example plans (src/app/ui.js, `pickExample` in src/app/main.js, `planHash` in src/app/params.js)

The plan on show is pressed (`aria-pressed`); a plan that came from a file leaves both unpressed. ## 6e. Floors on show (src/app/floors.js, `setFloor` in src/app/main.js)

A plan with two or more levels has a row of floor buttons: one per level and a last one for all of them. The choice is `'all'` (the default: every level drawn, the page as it was before the buttons) or the index of one level (0 is the lowest). It is nothing but data: `floor=0|1|...|all` in the address (`parseFloorParam` in `params.js`: a whole number from 0 to 99 or `all`, anything else is `all`; `resolveFloor(sel, count)` turns a level that the plan does not have, and every choice for a plan with fewer than two levels, into `all`). `floorHash(hash, sel)` writes it (`all` takes it out, every other parameter stays); `buildHash` writes it, `editHash` keeps it (or takes it from `state.floor`), and `planHash` takes it out, because a plan that is picked or loaded starts with all its floors on show. `visibleFlags(sel, count)` gives one boolean per level.

- **Buttons** (`createUI` in `ui.js`). The group `.floors` sits in the tools row after the example plans: `button.tool.floor` with `data-floor` (`0`, `1`, ..., `all`), `aria-pressed` for the choice on show, a title and an `aria-label`, at least 44 px like every tool button. They are rebuilt when `state.levels` (the names of the levels) changes and hidden when the plan has fewer than two. They stay on the bar while editing. `floorChoices(names, lang)` gives the words: the name of the level (`levels[].name`; in Polish "Ground floor" is Parter, "Upper floor" and "First floor" are Piętro, Basement and Attic are Piwnica and Poddasze, other names are kept; a level without a name of its own is Level N / Poziom N), cut to 18 characters on the button and complete in the title; the last button reads Both / Oba for two levels and All / Wszystkie for more. A tap calls `handlers.onFloor(key)`.
- **What a change does** (`setFloor`). The level groups of the others are hidden (`PlanScene.setLevelVisible`, which also switches off the window light of their panes: `paneLit`, so a cut of the walls does not light it again); the pieces follow without a new merge: `mergeByMaterial` lays the geometry of each merged mesh out level by level and records the stretch of each level in `mesh.userData.levelRanges`, and `showMergedLevels(group, shown)` cuts the draw range of every mesh to the stretch of the levels on show (a mesh with nothing on show is hidden; the footprints of `contact.js` are one mesh with the same ranges). The pieces that are objects of their own (the one being dragged, pieces hung on a turned wall, every piece with `merge=0`) are hidden through `furn.own`, and the hung ones through `shell.setLevels(flags)`. The lamps are kept by level (`emittersByLevel`) and the stage gets those of the floors on show only. The number of meshes, draw calls and geometries does not change: with all floors on show the duplex draws 1049 calls, as before, and 622 with only the ground floor and 556 with only the upper one (medium quality, 960 x 600).
- **The base of the house.** An upper floor that stands alone must not hang in the air: `floorLift(model, flags)` is how far the bottom of the lowest slab on show lies above the bottom of the lowest slab of the house (0 for the ground floor or all of them), and `stage.setLift(dy)` raises the whole base of the stage by that much: the card board, the table, the light rig and the lamps (the stage keeps the lamps in world coordinates and lowers them by the lift, so a lamp stays where the lamp is). Everything else keeps its place in the world, so picking, dragging and the outlines of the editor need no change. `window.__floors.lift()` reads it.
- **The camera and the cutaway.** `visibleExtent(model, full, flags)` is the box of the floors on show (x and z from the end points of their walls, y from the lowest slab on show to the top of the highest level, `floorY` the floor of the lowest level on show; with all floors it returns `full` itself). The page keeps `ext` (that box), `frameExt` and `framePts` (with the shell: the closed floors on show and their walls lying flat) for it, so the camera fits the floors on show (`frameCamera` fits whenever the choice is not `all`, the turn and the tilt stay, the distance and the target are those of the fit, and the move of the person stays), the pan limits and the board follow (`boardOf` takes only the walls of the floors on show), the cutaway cuts the walls and hides the hung pieces for that box (`recut` and `settle` run again only when the ground of the floors on show differs from the last one, `sameGround`; for the example duplex, whose floors stand on the same ground, a change is a change of visibility, a fit and a board), and `cameraFor` aims at `ext.floorY` when a single storey is framed. The stage itself is made once for the whole house.
- **Open the shell.** It works with any choice: the walls of the hidden floors still turn, out of sight (their level groups are hidden), the board holds only the walls of the floors on show, and the pieces hung on the walls of a hidden floor stay hidden whatever their wall does.
- **Editing.** A piece, or a room, of a floor that is not on show cannot be picked or hit (`hiddenNow`, `roomHitAt`), a change of floors clears a selection that belongs to the floor that goes (`onFloorChange`), `viewPoint` ignores hidden floors and, with some floors hidden, falls back to the highest floor on show so that Add puts the new piece there. Undo, redo, saving and loading a layout do not care which floors are on show. The Edit button keeps `floor=`.
- **For test tools.** `window.__floors = { get(), set(v), count, visible(), lift() }` (`get` gives `'all'` or the index, `set` takes a number, a numeric string or `all` and returns the choice now, `visible()` lists the indices of the levels drawn); `window.__planInfo()` also gives `floor` and `visibleLevels`, and `window.__shell.project()`, `shadow()` and `extent()` look at the floors on show. `tools/interact.mjs` taps every button on the duplex (`floorsBlock`, in `--btn` and alone with `--floors`; with `--edit` it runs `floorsEditBlock`): each tap checks the hooks, the address, that the turn and the tilt stay, that the floors on show fit in the picture above the controls and that the picture changed, with the shell open too, in Polish, and that Both brings the first picture back.

## 6f. Share link (src/app/share.js, `buildLink` and `shareLink` in src/app/main.js, `copyText` and `showLinkDialog` in src/app/files.js)

The Copy link button of the control bar (and File, Copy link in the edit bar) makes an address that carries the layout of the page. `share=` in the hash holds `{ v: 1, plan?, layout }` as JSON, deflated with the browser's own `CompressionStream('deflate-raw')` and written in base64url (`z1.<text>`); a browser without that stream writes the JSON undeflated (`u1.<text>`). Nothing leaves the page: the hash is not sent to a server and nothing is stored.

- **What goes in.** `layout` is `packLayout(serializeLayout(layout))`: the saved text of the layout (the editor's, or the auto layout when not editing) without what `parseLayout` fills in by itself (a size equal to the size of the type, the default height, no turn, no support, no colours, the seed 1). `plan` is present only for a plan of your own (`linkPlan` in main.js: from Load plan or from an opened link; null for an example plan, which `plan=` names): `planForLink` turns the normalized plan back into what the validator reads, without the derived fields and with the numbers rounded to 0.1 mm. The view goes in ordinary parameters (`setViewParams`: `preset`, `t`, `az`, `pol`, `floor`, `plan`, `seed`; defaults left out; the language and the quality stay the visitor's own). The link to send is clean (only these); the address bar keeps every other parameter of the page (`edit=1` among them), so a reload or the Edit button keeps the layout. The address also follows the editor (`src/app/addrsync.js`, `addr` in `main.js`): every `structure` or `dragend` change of the session writes the link into the address 400 ms after the last change (`replaceState`, no clipboard, no line to the visitor; builds are queued and never overlap), and Done awaits `flush()` before it reloads, so a changed colour or a turn survives Done without any save step. A plan of your own that was loaded on the page and has no address yet goes in at the next Edit or Done. Only when the layout cannot go in the address (too large, or an address that cannot change) does Done say so and ask for a file or a second tap, and a piece that stands outside every room is announced the same way before it is dropped.
- **Opening.** `main.js` runs inside an async function so that `decodeShare` can use `DecompressionStream`. The plan goes through `readPlanText`, the layout through `parseLayout(text, model)` (every piece checked against the plan: unknown types, positions outside the room, bad ids, supports and colours are left out with a warning). A link that cannot be read (`decodeShare` gives an error, a plan or a layout is refused) leaves the page as an example plan with the automatic layout, and one line (`startNotes`) says what happened. The room colours of a layout now go to the scene at the start (`applyRoomColors` was only called by the editor before).
- **A link is untrusted input.** The value has a limit (`SHARE_MAX_VALUE` 400 000 characters), the unpacking stops at `SHARE_MAX_TEXT` (a plan and a layout at the file limit, about 4 MB) while it streams, so a small deflated text that unpacks to gigabytes is stopped; `__proto__` keys are only data; a text nested more than `MAX_DEPTH` (40) levels is refused (an iterative walk, because JSON.parse copes with a million levels and the recursive readers after it do not); every reading of the plan and the layout in main.js is guarded, so whatever a link holds the page opens; no text of a link is put in the page as markup (the source has no `innerHTML`). The room colours of a link are applied before the first frame, so `PlanScene._spans` tests the box of each room before the polygon (a plan of 600 wall pieces and 150 rooms took minutes without it).
- **Length.** About 1 700 characters for the example flat, 2 600 for the duplex, plus 900 to 1 300 for a plan of your own (`tests/app/share.test.mjs` keeps a budget). Over `SHARE_LONG` (4 000) the page adds a word about messengers that cut long links (some chat apps take only 2 000 characters a message); above `SHARE_MAX_VALUE` the button says the layout is too large for a link.
- **Copying.** `copyText` tries `navigator.clipboard.writeText` (secure pages only), then `execCommand('copy')`; when neither works `showLinkDialog` shows the link in a field that selects itself, with a Copy button. `window.__share` (`build()`, `copy()`, `last()`, `notes`) is for the test tools.
- `planHash` (another example plan) and `applyPlan` (a loaded plan) drop `share=` from the address; `editHash` and `floorHash` keep it. A `hashchange` to another `share=` than the page was built from (or last wrote) reloads the page, so a link pasted into the address bar of an open tab takes effect.
- A plan from a link is built under a guard in main.js (`openWith`): if it cannot be built the page opens with the example plan and one line says so. `buildLink` counts the pieces that the receiver would refuse (`lostCount` of `parseLayout` on the packed layout) and the message after the copy says how many; `planForLink` leaves `meta` out and never rounds a positive number to zero.

## 8. Design decisions

- `kitchen-sink`: `size[2]` (default 1.1, range 1.05 to 1.2) includes the tap. The worktop sits at `size[2] - 0.2` (0.9 by default, level with `kitchen-base`), the tap rises 0.2 above it. The layout engine only cares about the footprint, so nothing else changes.
- Completeness in `checkLayout` (`REQUIRED_SETS` in `src/layout/check.js`): a room is complete when it holds the pieces of its recipe. Small rooms are excused from three pieces, to keep the recipes honest about space: a wardrobe is required from 10 m2 of interior, a nightstand from 2.4 m of width, a shower or bathtub from 3.5 m2. Living rooms always need a sofa, a TV unit, a coffee table and a rug; kitchens a fridge, sink, hob and base cabinet; bathrooms a toilet and a washbasin.
- `layout.seed` changes colours only. Positions come from the recipes without randomness, so every seed gives the same arrangement. Layout variants per seed belong to the editor.
- The input plan's own furniture is ignored: the engine furnishes, `src/render/compose.js` places the pieces (one `buildPiece` group per layout piece, `rotation.y = -rot * PI / 180`, `y = level elevation + elev`), and lamp emitters go to `stage.setEmitters`.
